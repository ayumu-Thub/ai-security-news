CDCSecurity for AIAIサプライチェーンSBOMモデルセキュリティ

AIモデルは「部品」として持ち込まれる——CDCが担うべきAIサプライチェーンExposure管理

AIモデルは外部から調達する「部品」である。偽モデルリポジトリ事例とCISA/G7のSBOM for AIガイダンスを踏まえ、CDCが担うべきAIサプライチェーンのExposure管理を3層モデルで整理する。

はじめに：モデルという「部品」がなぜExposureになるのか

AIを活用するシステムが増えるにつれ、組織のインフラにAIモデルが組み込まれる機会が増えています。社内RAGシステムのエンベディングモデル、コード補完や調査自動化の基盤モデル、MDRや脅威インテリジェンス分析に使うLLM——これらの多くは、外部から取得して使われています。

問いたいのは、そのモデルがどこから来ているかです。

ソフトウェア開発では、オープンソースのライブラリやサードパーティコンポーネントのセキュリティ確認が運用上の常識になってきました。SBOMの整備、依存関係スキャン、CVEへの対応——これはソフトウェアサプライチェーンのセキュリティです。

AIモデルは、同じ意味での「部品」です。外部から調達され、検証なしに使われれば、それはExposureになります。しかしこの視点が、ソフトウェアライブラリほどの当たり前さでAIモデルに向けられているかというと、まだそうなっていないと感じています。

本稿では、実際の事例と3層のExposureモデルを通じて、CDCが担うべきAIサプライチェーンのExposure管理を整理します。

事例：信頼されたプラットフォームを悪用する手口

2026年5月、Hugging Face上に偽のOpenAI公式リポジトリが確認されました。そのリポジトリには、OpenAIのブランドを模したモデルファイルが公開されており、内部には実行時に外部への接続を試みるコードが含まれていたとされています。

これを「Hugging Faceが危険」と読むのは正確ではありません。問題は、信頼されたオープンモデルリポジトリが、攻撃者による悪意あるコンテンツの配布経路として悪用され得るという構造です。

攻撃の形は単純です。名前を模した偽リポジトリを公開する、あるいは正規リポジトリを改ざんする——そこから取得したモデルを、出所確認なしに自組織のシステムに組み込む。これにより攻撃者は、モデル本体だけでなく、付随スクリプト、ローダー、依存ライブラリなどを通じて、実行環境に悪性コードを持ち込む可能性があります。

重要なのは、この種の攻撃が特別な標的型攻撃ではないという点です。攻撃者の関心は「誰かが確認なしにモデルを取得すること」にあります。利用組織が特定されていなくても成立する、サプライチェーン攻撃の構造を持っています。

ソフトウェアの世界でも、npmやPyPIへの悪意あるパッケージ公開が繰り返されてきました。AIモデルのリポジトリが同様の問題を抱えるのは、構造上の必然です。

AIサプライチェーンのExposureを3層で考える

この種のリスクを整理するために、私は3層のExposureモデルで考えることにしています。

Layer 1：調達・モデル層

どこからモデルを取得しているか、取得したモデルの整合性を確認しているか、ライセンスと利用条件を把握しているかという層です。

具体的には、モデルのソース（公式か非公式か）、ハッシュ値による改ざん確認、リリース元の確認、更新・変更の追跡が問われます。多くの組織でこの確認が最も薄い層です。「モデルをダウンロードして使う」という感覚が残っている間は、ここに穴が開きやすい。

Layer 2：実行基盤層

モデルが動作する環境の権限、隔離、モニタリングに関わる層です。

どのプロセスでモデルが実行されているか、実行環境がどの程度隔離されているか、ファイルシステムやネットワークへのアクセス範囲、リソース利用の異常を検知できるかが問われます。

Layer 1のチェックが通り抜けた場合でも、ここで実行時の異常挙動を検知できれば被害を限定できます。実行基盤の設計は、技術的な最終防衛ラインです。

Layer 3：接続・影響層

モデルが接続する先——業務システム、データストア、APIキー、OAuthトークン、NHI（Non-Human Identity）——に関わる層です。

モデルを経由した侵害が最終的にどこまで達するかは、この層の設計次第です。接続先が広いほど、Layer 1・2を突破されたときの影響範囲が大きくなります。

この層の詳細——NHI管理、MCP経由の接続制御、OAuthスコープの設計——はそれぞれ独立して論じるべきテーマです。本稿では、AIモデルの利用が接続・影響層と結びつくという問題の所在を確認するにとどめます。

SBOM for AI——監視設計のインプットとして何を期待するか

2026年5月、CISAとG7パートナー機関がAIシステム向けのSBOM（Software Bill of Materials）ガイダンスを公開しました。AIシステムを構成する要素——モデル、データセット、依存ライブラリ、学習・推論に関わる構成情報——を可視化するためのガイダンスです。

このガイダンスをどう読むかについて、一点整理しておきたいことがあります。

SBOM for AIを「組織が整備すべきゴール」として受け取ると、作業のスコープが広がりすぎます。ソフトウェアのSBOMでさえ、実運用での維持には相当のコストがかかります。モデルの学習プロセスやデータセットの系譜まで含めれば、さらに困難です。

私が有用だと思っているのは、SBOM for AIを監視設計のインプットとして使う読み方です。

「何をインベントリしておくべきか」を考える際の整理軸として使う。どのモデルがどの環境で動いているかを記録する際の項目として参照する。調達・取得プロセスに何を追加すべきかを議論する際の出発点にする——こうした使い方は、SBOM for AIの完全な整備が難しい組織でも現実的です。

CISA/G7ガイダンスが示しているのは、「AIシステムの可視性を持つことが、セキュリティ管理の前提である」という考え方です。その可視性をどのレベルから始めるかは、自組織の状況に合わせて考える余地があります。

CDCとしての当面の対応

Layer 1・2を中心に、CDCとして今取り組める対応を整理します。なお、AIサプライチェーン管理はCDCだけで完結するものではありません。調達、開発、情シス、AIガバナンス部門と連携しながら、CDCは監視・変更検知・影響分析の観点からExposureを把握する役割を担います。

まず、インベントリを作ること

自組織でどのAIモデルが、どこで使われているか——この一覧が作れない状態からは始まりません。内製システムに組み込んでいるモデル、外部AIサービスとして利用しているモデルやサービス、開発環境で試験的に使われているモデル。分類の仕方はいくつかありますが、「使われているAIモデルの一覧を作れるか」が出発点です。

SBOM for AIのガイダンスは、このインベントリ作成の項目整理として使えます。全部を一度に埋める必要はなく、まずモデル名・取得元・使用環境・更新状況を押さえることから始めるのが現実的です。

取得プロセスに確認ステップを入れること

モデルを取得する際の確認を、運用プロセスに組み込みます。ソース（公式リポジトリか、検証済みソースか）の確認、ハッシュ値による整合性確認、モデルの変更履歴の確認——これをチェックリスト化して、取得・更新の都度確認するだけでも、Layer 1の穴は塞がります。

「モデルをダウンロードしてそのまま使う」という状態から「確認してから使う」状態への移行が、現時点では最も影響の大きい対応だと考えています。

実行環境の設計を見直すこと

モデルがどの権限で動いているか、実行環境が外部ネットワークに無制限にアクセスできる状態になっていないか、異常なプロセス起動やネットワーク接続を検知できる監視が入っているかを確認します。

既存のEDR・NDRの監視範囲に「AIモデルの実行プロセス」が入っているかどうか、一度確認する価値があります。Layer 2の隔離と監視は、モデル固有の対応というよりも、実行基盤のセキュリティ設計の延長線上にあります。

Layer 3として残る接続・影響の問題

Layer 3——接続・影響層——への言及を最後にしておきます。

モデルが業務システムやデータストア、APIキーに接続している場合、モデル経由の侵害の影響範囲は接続先の設計に強く依存します。NHIとして管理されるAPIキーやOAuthトークン、MCPサーバーを介したエージェント連携——これらはLayer 3の具体的な要素です。

AIエージェントとモデルの利用が重なるこの領域は、前のコラム（「AIエージェントは、誰が監視するのか」）で扱ったNHIやエージェントID管理の議論とも接続します。ただし、NHI管理・MCP接続制御・OAuthスコープ設計はいずれも独立した論点であり、本稿では問題の所在を示すにとどめます。

おわりに：「部品管理」の視点を持つことから

AIモデルは外部から調達する部品です。この認識を持つと、セキュリティ管理の問いが自然に出てきます。どこから来たのか。整合性は確認したか。どの環境で動いているか。何に接続しているか。

ソフトウェアライブラリのサプライチェーンセキュリティが当然視されてきたように、AIモデルに同じ問いを向けることが、AI活用を進める組織には求められるようになっています。

CDCが関与すべき領域は、すでに「AIを活用する」側だけでなく「AIを監視・管理する」側にも広がっています。モデルのインベントリ作成、取得プロセスへの確認ステップの組み込み、実行環境の権限設計——ここから始めることは、今日でもできます。

「部品として持ち込まれるモデルを管理する」という視点を、CDCの設計にどう組み込むか。その問いを持つことが、AIサプライチェーンExposure管理の出発点だと考えています。
